# Contributing to cbom-netscan

Thanks for helping. This page covers the three rules that matter most (sign
off your commits, keep the tests passing, never commit real configurations)
and how to work on the code.

## Never commit a real configuration

Configuration backups contain secrets, addresses, and network layout. **Do
not commit, attach, or paste a real backup, or any part of one**, anywhere in
this project: code, tests, issues, pull requests, or discussions. Redacting
is not enough.

Test fixtures must be synthetic:

- written by hand from the FortiOS CLI reference, with made-up names;
- addresses from the documentation ranges (192.0.2.0/24, 198.51.100.0/24,
  203.0.113.0/24) and domains under `example.com`, `example.net`,
  `example.org`;
- secrets made up and recognisable as fake: the fixtures use base64 of
  strings starting with `synthetic` (which begins `c3ludGhldGlj`), and the
  secret-leak tests look for it;
- certificates generated by `pkg/fortios/extract/certs/testdata/gencerts.go`,
  which discards the private keys. Never commit a real private key, even a
  test one you generated: commit only certificates;
- no text copied from Fortinet's documentation or software beyond the field
  names, option tokens, and defaults the parser needs.

Fixtures are dedicated to the public domain (CC0-1.0, see `REUSE.toml`).

## Sign off every commit (DCO)

Every commit must carry a `Signed-off-by:` line, certifying the
[Developer Certificate of Origin](https://developercertificate.org/): that
you wrote the change or otherwise have the right to submit it under the
project's license. Let Git add it:

```sh
git commit -s
```

The name and email must be your real ones and match the commit author.
Pull requests with unsigned commits cannot be merged; to fix one, run
`git commit --amend -s` (or `git rebase --signoff main` for several) and
force-push your branch.

## Commits and pull requests

- Small commits, each building and passing the tests on its own.
- [Conventional Commits](https://www.conventionalcommits.org/) messages,
  with the package as scope, for example
  `fix(fortios/extract/certs): skip a byte order mark before a PEM value`.
  Use `fix` for anything that changes behaviour, even inside a test commit.
- Explain why in the message body, not only what.
- One topic per pull request. Open an issue first for larger changes.

## Tests

CI runs all of these; run them before you push:

```sh
go mod verify
gofmt -l .                     # must print nothing
go vet ./...
go run honnef.co/go/tools/cmd/staticcheck@v0.8.2 ./...
go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...
go test -race ./...
```

Also:

- **Golden files.** The CBOMs in `pkg/testdata/golden/` are compared byte for
  byte. If your change alters output on purpose, regenerate them with the
  package's `-update` flag (for example `go test ./internal/cli -run
  CertsSSLVPN -update`), read the diff, and explain it in the commit. CI
  validates every golden file with
  [cyclonedx-cli](https://github.com/CycloneDX/cyclonedx-cli) against the
  CycloneDX 1.6 schema.
- **Fuzzing.** Parser changes should survive the fuzz targets for a while,
  for example `go test -run='^$' -fuzz='^FuzzLexer$' -fuzztime=60s
  ./pkg/fortios/lexer/`. The targets are `FuzzLexer`, `FuzzParse`,
  `FuzzExtract`, and `FuzzScanCertField`.
- **Licensing.** Source files start with the same SPDX copyright and
  license header as the existing ones (Apache-2.0); `REUSE.toml` covers fixtures and
  documentation. `docker run --rm -v "$PWD":/data fsfe/reuse:latest lint`
  checks it.
- **New behaviour needs a test that fails without it.** Where it matters
  (secrets, parsing), also check the test catches a deliberate break.

## Rules for the code

- **Secrets never reach output.** Report that a secret is present, and in
  which form, never its value. Warnings and errors must not quote input that
  could contain one. Key material is never decoded; PEM values are
  classified by their header lines only. See MAPPING.md §6.9.
- **Do not guess FortiOS behaviour.** Field names, options, and defaults come
  from `docs/fortios-parser-research.md`, which cites the CLI reference or
  guide for each. If something is not documented there, report it as
  unknown, and add the source to the research notes when you find one.
- **Strict on secrets, lenient on structure.** A malformed section should
  give a warning and the rest of the backup should still be inventoried.
- Keep MAPPING.md in step with the output: a new property, warning, or
  component kind belongs there in the same pull request.
